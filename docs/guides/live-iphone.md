# Live iPhone capture

Stream an iPhone's LiDAR, camera and IMU into the native Modelica SLAM, and watch the
map grow in Safari. By default the phone does not send images: it picks out corner landmarks itself
and sends only those points (see [What the phone sends](#what-the-phone-sends)). The SLAM runs in a
desktop browser tab.

```
iPhone app ──ws──▶ relay (Mac, npm run live) ──ws──▶ SLAM tab (desktop browser, slam_web)
                          │                                    │
Safari on the phone ◀─────┴──────────── map, pose, graph ◀─────┘
```

Needs an iPhone with LiDAR (12 Pro or newer Pro models, including the 13 Pro) and a Mac with
Node 22 and Xcode. All devices must be on the same Wi-Fi.

## Run it

1. On the Mac you need Node 22 or newer and Git (`brew install node git`; check with `node -v`).
   Install from a clean checkout: do not copy a `node_modules` folder from another machine,
   its native binaries are platform specific. Then start the relay and the lab:

   ```sh
   npm ci && npm run assets
   npm run live          # prints the phone and Safari addresses
   npm run dev           # in a second terminal; open the printed http://localhost URL
   ```

   `npm run assets` downloads about 45 MB of native SLAM programs from GitHub; it needs internet
   access and is only required for the native SLAM (the page and relay run without it).
   Allow incoming connections for Node if macOS asks (System Settings → Network → Firewall).
   Add `--token=SECRET` to `npm run live` to require a token on every connection.

2. In the lab page, find **Live iPhone** (bottom row), keep the relay at
   `ws://localhost:8787/runner`, pick a camera mode and press **Start live capture**. The page
   switches to **Native Modelica SLAM** and recompiles. This needs a desktop browser with
   hardware rendering and about 1.2 GB per drone (see [Using the lab](using-the-lab.md#native-modelica-slam)).

3. Build and run the app on the iPhone (see [ios/README.md](../../ios/README.md)), enter the
   Mac's address from step 1 and tap **Start streaming**. The page shows
   "First phone frame received" and the SLAM starts. No phone yet? `npm run live:simulate`
   streams a stationary fake phone through the same wire format.

4. Open `http://<mac-ip>:8787/view.html` in Safari on the iPhone (or tap **Show map** in the
   app) for the mirror: point cloud coloured by height, trajectory, keyframes and loop edges,
   plus how far the SLAM is behind the camera. **Fit map** keeps the whole map framed, **Follow**
   tracks the phone, and touching the view frees the camera.

## What the phone sends

The page has a **Phone sends** setting; the choice reaches the phone as a `config` message through the relay.

- **Landmarks (default).** The phone resamples the frame to the camera mode, finds FAST corners,
  keeps the ones with a usable LiDAR return, and sends for each: pixel position, depth, selection
  score and a 7 × 7 brightness patch. About 38 KB per frame at the 350-landmark cap, instead of a
  JPEG plus a depth map. No camera image, depth map or confidence map leaves the phone.
  The page rebuilds a sparse frame (every sample zero except each landmark's patch and depth) and runs
  a landmark-input SLAM program that skips the image stages. Everything after corner selection
  (descriptors, matching, registration, mapping, loop closure) is the same Modelica as the image program.
- **Raw.** The previous behaviour: JPEG, depth and confidence. Useful for comparison and for
  recording full frames.

The landmark selection exists twice and must agree: `src/landmark-source.ts` (reference, tested) and
`ios/SlamCapture/LandmarkExtractor.swift`. Selection follows the image pipeline: absolute FAST-9
threshold `max(8, 18·min(1, width/848))`, depth qualification (0.28–10 m), ranking by score with ties by
raster index, square suppression of radius 3, border 3.

Checked on the synthetic frames with `scripts/landmark-equivalence.ts`: at 424 × 240 the landmark programs
reproduce the image programs' poses, matches and map sizes exactly (difference 0). The one deliberate
difference is that scores travel as float32. Not yet checked: the Swift port against the TypeScript
reference on real frames, quality on real phone data, and speed on a phone. The Swift code has not been
compiled in this project's environment.

Landmark programs live in `public/vendor/slam-landmark`. They are generated by
`scripts/generate-landmark-models.mjs`, exported with `scripts/export-landmark-profiles.mjs` and
published with `scripts/publish-landmark-assets.mjs`; the exporter needs Rumoca's `native_step`
example binary (see the header of that script). Only the resolutions listed in that folder's
manifest can run landmark mode; others need an export.

Known limitation: the landmark Step keeps the FAST scoring and depth-qualification calls even though
their result is unused, because with them removed Rumoca's native emission rejects every prediction.
On the phone's sparse frame this costs little, but it should go away once the compiler is fixed.
The cause is not understood.

## Zero-velocity update (resting phone)

The estimator is an error-state Kalman filter with no measurement that says "the phone is not moving", so
a small accelerometer bias on a resting phone integrates into position drift until a visual update or a
loop closure corrects it. The landmark programs add that measurement. The page's **Zero-velocity update
when the phone is at rest** box (on by default) flags frames in which the IMU shows a motionless device
(`isAtRest` in `src/live-source.ts`): mean gyro under 0.02 rad/s with no sample above 0.06, acceleration
noise under 0.05 m/s², and gravity within 0.3 m/s². For those frames each IMU step also applies a
velocity = 0 update (`ZeroVelocityUpdate` in `models/SLAM/RGBDLandmarkSLAM.mo`, σ = 0.02 m/s).

- The limits are strict on purpose: a phone held in a hand shakes more than this, so it is never declared
  at rest. A phone resting on a table or stand is.
- Checked in simulation (`scripts/landmark-zupt.ts`): a resting device with a 0.05 m/s² accelerometer bias
  drifts 2.5 m in 10 s with the update off and stays at the start position with it on. With the update off
  the programs match the image programs exactly (`scripts/landmark-equivalence.ts`).
- Not checked: real phone data, whether the thresholds fit your phone's noise, and loop closure after a
  long rest. The update skips the second-order attitude reset of the covariance, which is negligible for the
  tiny corrections of a resting device. It cannot fix a wrong IMU axis or gravity convention.
- It needs the landmark programs built with this change. Older programs have no `zeroVelocity` input and the
  page then silently runs without it.

## Speed, honestly

The native SLAM takes about 4 s for a new image and 0.25 s per held IMU interval on a desktop.
The estimator rejects camera gaps above 1 s and cannot skip IMU time, so the live link sends
frames 0.6–0.95 s apart with 0.2 s IMU intervals: roughly 5–7 s of compute per second of motion.
It is near-live, not real time.

- Frames are never dropped inside the queue. If the SLAM falls too far behind (200 MB of queued
  frames, about 130 frames at 640 × 480) the Mac tells the phone to stop and finishes the queue.
- Walk slowly and pause now and then; the map catches up while you stand still.
- **424 × 240** is the fastest mode and uses a third of the memory, at the cost of cropping the
  phone's 4:3 field of view to 16:9. **640 × 480** keeps the full field of view.
- Lower memory use and fewer evaluations help more than a faster Mac.

## What gets converted (raw mode, and the inputs to landmark selection)

| Phone | Lab |
| --- | --- |
| ARKit `sceneDepth` float32 metres, 256 × 192, confidence 0/1/2 | Z16 in millimetres, nearest-neighbour resampled onto the colour grid. Confidence below *medium*, depth under 0.2 m or over 5 m become 0 (no return). |
| `capturedImage` 1920 × 1440, sent as JPEG | RGB8, cropped to the camera mode's aspect and scaled. Intrinsics are scaled and shifted to match. |
| CoreMotion acceleration + gravity (g), rotation rate (rad/s), device axes | Specific force in m/s² and rate in rad/s, body axes forward-left-up. |
| ARKit and CoreMotion timestamps (shared clock) | Seconds from the first accepted frame; the first frame is the time-zero initial frame. |

The body frame is defined to coincide with the rear camera (forward = camera axis, up = the
image's up direction in ARKit's landscape-right sensor orientation), so no extrinsic rotation is
needed between camera and IMU. The small lever arm and any time offset are not calibrated; if
the estimate drifts, set `originFlu` or an IMU time shift in `src/live-source.ts` (`liveCalibration`).
ARKit's own pose is carried in each message but the estimator does not use it yet.

LiDAR is mapped onto the estimator's stereo noise model with `baselineMeters = 0.05` and
`depthNoiseDisparityPx = 0.1` (about 1.5 cm at 2 m). These are starting values to tune in
`DEFAULT_LIVE_CONFIG`.

## Wire format

Phone → relay → SLAM tab, on `/ingest`:

- **IMU** (text): `{"type":"imu","samples":[[t, ax, ay, az, gx, gy, gz], …]}` with CoreMotion
  values in the device frame (g, rad/s).
- **Camera** (binary): `uint32 0x31485049 ('IPH1') | uint32 headerLength | JSON header | JPEG |
  float32 depth (little endian) | uint8 confidence`. The header is
  `{"type":"camera","t":seconds,"color":{"width","height","fx","fy","cx","cy"},
  "depth":{"width","height"},"jpegBytes","depthBytes","confidenceBytes","pose":[16 floats]}`.
- **Landmarks** (binary, landmark mode): `uint32 0x314C5049 ('IPL1') | uint32 headerLength | JSON header |
  x uint16[n] | y uint16[n] | z uint16[n] (depth, mm) | score float32[n] | patch uint16[n × 49]`, little
  endian. The header is `{"type":"landmarks","t":seconds,"count":n,"color":{"width","height","fx","fy","cx","cy"},
  "target":{"width","height"},"pose":[16 floats]}`. Pixels are in the target (SLAM) raster, at least 3 px from
  the border; each patch value is the sum of r+g+b of a 7 × 7 window (0–765). The relay forwards it unchanged.
- **Config** (text, page → relay → phone): `{"type":"config","mode":"landmarks"|"raw","resolution",
  "width","height","minConfidence","nearMeters","farMeters","depthUnitsMeters","landmarkCapacity",
  "fastThreshold","frameIntervalSeconds"}`. The relay keeps the latest and replays it to a phone that
  connects later; a phone that gets none within 3 s falls back to raw frames.
- Camera sections must add up exactly to the message length; the SLAM tab rejects anything else.

SLAM tab → relay (`/runner`): `{"type":"state",…}` JSON for pose, keyframes, edges and progress,
and binary `uint32 0x31535450 ('PTS1') | uint32 count | count × (x, y, z) float32` for the map,
at most 40,000 points. Viewers (`/view`) receive both. Control messages
`{"type":"control","action":"stop","reason":"buffer-full"|"gap"}` go back to the phone.

## Troubleshooting

- **Page cannot reach the relay**: use the relay address printed by `npm run live`. A page served
  over `https` cannot open `ws://` (Safari blocks it): open the lab from `npm run dev` over `http`.
- **Phone cannot connect**: same Wi-Fi, firewall allows Node, and iOS asked for Local Network
  access (Settings → SLAM Capture → Local Network).
- **"camera frames are … apart"**: the connection stalled for over a second. Press Stop and start again.
- **Camera mode mismatch**: the page recompiles for the chosen mode; wait for it to finish. In landmark mode the page refuses a packet whose target size differs from the SLAM resolution.
- **"does not accept landmark inputs" or missing landmark assets**: the landmark programs for that resolution are not installed; use Raw or export them.
- **Browser features on the phone** (DeviceMotion, getUserMedia) need HTTPS, but the native app
  and this mirror do not. To serve the mirror over HTTPS anyway, start the relay with
  `--cert=cert.pem --key=key.pem` (for example from `mkcert`).
